# 저장소 작업 지침

사람과 AI 작업자가 함께 지키는 규칙입니다. 절차의 상세는 링크한 문서가 단일 기준이며 여기서는 반복하지 않습니다.

## 시작할 때

- 저장소 루트에서 `python3 project/tools/setup_git.py`를 한 번 실행해 커밋 훅과 루트의 로컬 파일 제외 규칙을 적용한다.
- 현재 소스·문서·원격 이력과 요청 범위를 먼저 확인한다. 전체 범위는 [문서 안내](README.md), 구조·영향 범위는 [기술 구조](dev/architecture.md)를 본다.
- 답변·문서·커밋·PR·이슈·리뷰·결과 보고는 한국어로 쓴다. 식별자·명령·오류 원문은 원래 표기를 유지한다.
- 현재 구현·원격 반영·실제 배포·계획을 구분한다. 설정 등록을 배포 성공으로, 자동 검사를 사람의 원문 대조로, 기능 검사를 독자 성과로 표현하지 않는다. 이전 날짜의 검증 수치는 당시 근거로 보존한다.

## 브랜치·커밋·PR

- 기능 하나를 작업 브랜치 하나와 `main` 대상 PR 하나로 관리한다. 문서만 요청된 작업은 자체 PR로 묶고, 커밋은 폴더·역할·검증 목적별로 나눈다. [커밋 기준](dev/commits.md)
- `main`에 직접 수정 커밋을 만들지 않는다. 일일 자료는 아래 절차로 선별 반영한다. PR은 해당 SHA의 `verify-ci`를 확인한 뒤 병합한다. Vercel 미리보기(dev)는 기본 절차가 아니며, 병합 전에 화면을 직접 봐야 할 때만 같은 커밋을 `dev/<이름>` 브랜치로 push해 붙인다. 미완성·배포 보류 기능은 작업 브랜치에 남긴다. [브랜치·배포](dev/branches.md)
- 코드·데이터·기준 브랜치가 바뀌면 다시 검사한다. 검사 우회와 다른 SHA의 성공 기록 재사용을 금지한다. 병합·Pages 배포·공개 `build-info.json` 확인 결과는 각각 기록한다.

## 일일 발행

- 기사 데이터는 안정 `main` 기반 `daily/YYYY-MM-DD`에서 준비하고, 오늘 JSON·색인·실제 추적 갱신만 선별 발행한다. 일일 작업으로 코드·워크플로·검사·과거 호를 바꾸거나 브랜치 전체를 운영에 병합하지 않으며 기능 릴리스 태그를 만들지 않는다.
- 06시 기사는 검토를 기다리지 않고 검사 후 자동 발행하며 `review.auto: true`로 사람의 원문 대조와 구분한다. 사람이 확인하지 않은 호에 확인자 이름을 만들지 않는다.
- 감독 예약은 05:55에 깨어나 도구를 준비하고, GitHub 예약을 기다리지 않고 06:00:00 정각에 안정 `publish.yml`을 실행한 뒤 공개(예상 06:04~06:07, 배포 전 전체 검사 포함)를 확인하며, 실패하면 재시도로 복구한다(2026.11.05·11.19 사용자 승인). 06:00 전에는 실행하지 않는다. 진행 중인 같은 실행은 중복 요청하지 않으며 코드·기사 임의 수정·검사 우회·빈 push·강제 push는 하지 않는다.
- 발행 실패는 [런북의 장애 추적 순서](planning/runbook.md#장애-추적-순서)대로 코드·데이터·예약 지연·배포를 구분해 진단하고, 해결하지 못한 원인·실행 기록을 보고한다.

일일 발행에 필요한 세부 기준은 다음 문서에서 확인한다. [런북](planning/runbook.md) · [초안 편집 기준](planning/editorial.md) · [데이터 규격](planning/data-spec.md)
