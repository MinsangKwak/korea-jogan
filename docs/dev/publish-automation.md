## ① Codex 00:00 조사·초안·편집

1. 한국 시간 오늘 날짜와 원격 `main` SHA를 확인합니다. `dev`에서 일일 브랜치를 만들지 않습니다. 같은 날짜의 `daily`가 이미 있으면 상태·SHA를 읽고 덮어쓰지 않습니다.
2. `main` 기준의 `daily/YYYY-MM-DD`에서 전날 23:59까지 새로 수집한 자료로 오늘 초안을 작성합니다. 과거 대화·전날 자료를 오늘 확인한 사실처럼 쓰지 않습니다.
3. 사실 초안을 임시 JSON으로 보존하고 `validate.py`를 통과시킵니다. 원문과 대조하며 허용된 설명 문자열만 편집한 뒤 `check_editorial.py --baseline-file`과 `validate.py`를 실행합니다.
4. 오늘 JSON·발행 색인과 실제 근거가 갱신된 `trackers.json`만 반영합니다. 초안+색인과 추적 갱신은 역할별 커밋으로 나눕니다. 코드·문서·과거 호·승인·정정 자료를 섞지 않습니다.
5. 대상 일일 브랜치의 시작 SHA가 그대로일 때만 예상 SHA 기반으로 반영합니다. 브랜치 생성 충돌·동시 변경·검사 실패는 덮어쓰지 않고 보고합니다. 일일 조사에는 별도 PR 승인 단계를 두지 않습니다.
6. 원격 오늘 브랜치·호·색인과 고정 SHA의 CI를 확인해 머리기사·주제·기사 수·대체한 매체·검사·반영 여부를 짧게 보고합니다. `main`·`deploy` 직접 수정이나 승인 명령을 실행하지 않습니다.

[상세 편집·보존 검사](../planning/editorial.md)를 따릅니다. 이미 공개된 호는 자동 재작성하지 않으며 빠진 날짜를 소급 생성하지 않습니다. 조사 시작 뒤 운영의 오늘 호·추적 자료가 바뀌면 아침 선별 검사도 충돌을 차단합니다.

## ② Codex 06:05 공개 확인

현재 역할은 공개 날짜·워크플로 기록의 **읽기 전용 확인**입니다. 원래 인수인계에는 `publish.yml`을 `ref=main`으로 직접 실행하는 역할이 있었지만 현재 연결 도구에 `workflow_dispatch`가 없고 GitHub CLI 인증도 없습니다. 기존 성공 작업 재실행으로 대체하려던 확인은 자동 승인 검토에서 거절됐습니다. 직접 실행은 별도 명시적 승인·사용 가능한 실행 경로 확인 전까지 활성화하지 않습니다.

- 3~5분 뒤 공개 색인 `https://korea-jogan.com/data/issues/index.json`의 `latest`가 한국 시간 오늘인지 15초 간격으로 최대 6분 확인합니다. 대기는 한 번에 60초 이하로 나눕니다.
- 공개됐으면 한 줄 결과만 남기고 별도 성공 알림은 보내지 않습니다.
- 공개되지 않으면 오늘 일일 브랜치 → JSON·색인 → 고정 SHA의 CI → 선별 검사·동시 변경 → 안정본·Pages 순서로 진단하고 실패 이유를 알립니다. 공개 `build-info.json`의 실제 소스 SHA·호 날짜도 대조해 이전 배포와 오늘 배포를 구분합니다.
- 코드·데이터 수정, 빈 커밋·push, 강제 push, 기존 예약 해제로 우회하지 않습니다.

실제 발행은 GitHub의 기존 재시도가 담당합니다. 예약 지연 자체가 감독 작업에 소스 수정 권한을 주지는 않습니다.

## 저장소 워크플로와 안정 코드

| 파일·기능 | 책임 |
| --- | --- |
| [check.yml](../../.github/workflows/check.yml) | 개발·안정·일일 커밋의 데이터·브라우저 등 CI |
| [publish.yml](../../.github/workflows/publish.yml) | 안정 `main`에서 오늘 `daily` SHA를 고정하고 CI·허용 파일·동시 변경 검사 후 데이터만 공개 |
| [prepare_daily.py](../../dev/pipeline/publish/prepare_daily.py) | 오늘 JSON·색인·실제 추적 변경의 제한된 가져오기. 소스 코드 실행·전체 병합 금지 |
| 코드 승격 | 검토한 정확한 `dev` SHA의 CI·Vercel 배포·운영자의 인증/관리자 확인·조상 관계 확인 |
| [deploy-pages.yml](../../.github/workflows/deploy-pages.yml) | `deploy` 기준 공개 파일 생성·Pages 배포 |
| [daily.yml](../../.github/workflows/daily.yml) | 수동 RSS·ECOS 수집. 조사 예약을 대체하지 않음 |

아침 발행은 일일 소스 SHA의 `data`·`browser` 성공을 확인합니다. 안정 코드의 오늘 호가 이미 공개됐으면 중복 발행하지 않으며, 날짜·상태·색인·허용 경로·운영 동시 변경이 어긋나면 중단합니다. 미확인 초안은 검사 후 `approve.py --auto`로 공개하고 `review.auto: true`를 남깁니다. 사람 이름을 만들어 확인자로 적지 않습니다.

`GITHUB_TOKEN` push만으로 후속 워크플로가 실행되지 않으므로 새 운영 자료를 반영한 뒤 배포를 명시적으로 호출합니다. 소스 브랜치에서 바뀐 워크플로나 검사 코드를 아침 발행 코드로 사용하지 않습니다. 배포 작업은 실제 체크아웃한 `deploy` SHA·호 날짜를 공개 빌드 정보에 남깁니다. 수동 호출 응답만으로 공개 완료를 기록하지 않고 해당 SHA의 실행 성공과 빌드 정보를 확인합니다.

## 이관 뒤 확인 순서

1. Codex 예약의 `daily` 지시 갱신과 실제 활성 상태를 확인합니다.
2. 첫 00시 실행에서 안정 `main` 기준 브랜치·허용 파일·역할별 커밋·CI를 확인합니다.
3. 첫 아침 발행에서 고정 소스 SHA·선별 가져오기·자동 발행 표시·운영 배포 날짜를 확인합니다.
4. 개발 코드가 바뀐 날에도 일일 데이터만 안정 코드에 반영되는지 확인합니다.
5. `ECOS_API_KEY`·Pages 환경은 실제 설정을 유지하고, 키·토큰을 저장소에 넣지 않습니다.

## 이전 구조의 장애 기록

2026.11.03 이전 방식은 `dev` 전체를 `main`·`deploy`로 빨리 감기했습니다. 당시 `main` 병합 커밋이 `dev`에 포함되지 않아 아침 발행이 멈춘 기록과, 2026.10.23의 예약 지연 기록이 인수인계에 남아 있습니다. 이는 **당시 구조의 원인과 복구 사례**이며 현재 일일 브랜치를 `dev`에 합치라는 지시가 아닙니다.

새 구조에서는 일일 자료를 안정 코드에 선별 반영하고, 코드 승격의 조상 관계를 따로 확인합니다. 이전 Claude 예약을 나중에 복구하려면 운영자의 별도 요청에 따라 담당을 하나로 정하고 Codex와 중복 실행되지 않게 합니다. 빠진 날짜는 소급 생성하지 않습니다.
