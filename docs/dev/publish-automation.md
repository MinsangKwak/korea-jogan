# 일일 발행 자동화 구성과 이관 지침

**00시 Codex가 안정 코드에서 오늘 자료를 만들고, GitHub 아침 발행이 그 데이터만 운영에 반영합니다.** 개발 코드 검토와 매일의 뉴스 발행을 분리합니다. 시간은 한국 시간입니다.

[발행 런북](../planning/runbook.md) · [조사·편집 기준](../planning/editorial.md) · [브랜치 절차](branches.md) · [개발·운영 환경](environments.md)

## 기능 개발·승격의 공통 지침

2026.11.05 사용자는 기능별 브랜치·커밋·PR, 전체 자동 승격과 검토 없는 정시 기사 배포를 요청했습니다. 실행 환경과 브라우저 엔진의 반복 시작을 없애는 구조는 [자동화 구조](delivery.md)를 따릅니다.

| 단계 | 자동화 작업이 지킬 기준 |
| --- | --- |
| 기능 브랜치 | 기능 하나당 `feature/<기능명>` 하나. 폴더·역할·검증 목적별 한국어 커밋을 나눔 |
| 기능 PR | PR 하나에 기능 하나. 구현·기능 검사·배포 준비가 끝난 PR만 `dev`에 병합 |
| 통합 검증 | 최신 `main`·`deploy` 이력을 포함한 `dev`의 빌드·데이터·브라우저·관련 테스트와 같은 SHA의 보호된 개발 배포 확인 |
| 코드 승격 | 정확한 SHA를 고정해 `main`·`deploy`로 반영. 검증 뒤 코드·데이터·기준 브랜치가 바뀌면 재검사 |
| 기능 태그 | 검증 커밋에 고유한 태그를 남기고 이동·덮어쓰기 금지. 태그·Pages 성공·공개 빌드 SHA를 따로 확인 |

미완성·배포 보류 기능은 피처 브랜치에 남깁니다. `dev`를 승격하면 포함된 모든 기능이 함께 배포되므로 대상 목록을 먼저 확인합니다. 통합 워크플로는 전체 검사 뒤 같은 실행 환경에서 검사 증거·개발 배포·익명 차단을 확인하고 태그·main·deploy를 자동 반영합니다. [태그 정책과 현재 구현 범위](branches.md#태그-정책과-자동화-범위)

일일 기사 JSON은 아래 데이터 전용 경로를 유지하며 기능 릴리스 태그를 매일 만들지 않습니다. 조사 예약은 오늘 자료만 저장하고, 감독 예약은 미공개면 안정 발행 실행·재시도로 자동 복구합니다. 코드·기사의 임의 수정이나 검사 우회 권한은 주지 않습니다.

## ① Codex 00:00 조사·초안·편집

1. 한국 시간 오늘 날짜와 원격 `main` SHA를 확인합니다. `dev`에서 일일 브랜치를 만들지 않습니다. 같은 날짜의 `daily`가 이미 있으면 상태·SHA를 읽고 덮어쓰지 않습니다.
2. `main` 기준의 `daily/YYYY-MM-DD`에서 전날 23:59까지 새로 수집한 자료로 오늘 초안을 작성합니다. 과거 대화·전날 자료를 오늘 확인한 사실처럼 쓰지 않습니다.
3. 사실 초안을 임시 JSON으로 보존하고 `validate.py`를 통과시킵니다. 원문과 대조하며 허용된 설명 문자열만 편집한 뒤 `check_editorial.py --baseline-file`과 `validate.py`를 실행합니다.
4. 오늘 JSON·발행 색인과 실제 근거가 갱신된 `trackers.json`만 반영합니다. 초안+색인과 추적 갱신은 역할별 커밋으로 나눕니다. 코드·문서·과거 호·승인·정정 자료를 섞지 않습니다.
5. 대상 일일 브랜치의 시작 SHA가 그대로일 때만 예상 SHA 기반으로 반영합니다. 브랜치 생성 충돌·동시 변경·검사 실패는 덮어쓰지 않고 보고합니다. 일일 조사에는 별도 PR 승인 단계를 두지 않습니다.
6. 원격 오늘 브랜치·호·색인과 고정 SHA의 CI를 확인해 머리기사·주제·기사 수·대체한 매체·검사·반영 여부를 짧게 보고합니다. `main`·`deploy` 직접 수정이나 승인 명령을 실행하지 않습니다.

[상세 편집·보존 검사](../planning/editorial.md)를 따릅니다. 이미 공개된 호는 자동 재작성하지 않으며 빠진 날짜를 소급 생성하지 않습니다. 조사 시작 뒤 운영의 오늘 호·추적 자료가 바뀌면 아침 선별 검사도 충돌을 차단합니다.

## ② Codex 06:05 공개 확인

사용자는 예정 시각에 기사 발행·배포를 검토 없이 자동 완료하도록 승인했습니다. 과거 읽기 전용 제한과 실행 승인 대기는 이 범위에서 대체됩니다.

1. 현재 `main`의 지침·발행 워크플로, 한국 시간 오늘 날짜와 실제 공개 색인·호 JSON·홈·빌드 SHA를 확인합니다.
2. 오늘 호가 공개됐으면 한 줄 결과만 남기고 별도 성공 알림은 보내지 않습니다.
3. 미공개면 진행 중인 아침 발행·같은 소스의 Pages를 확인합니다. 이미 진행 중이면 중복 시작하지 않고 결과를 확인합니다.
4. 실행이 없거나 실패했다면 안정 `publish.yml`을 `ref=main`으로 실행합니다. 직접 실행 도구가 없으면 현재 `main`의 워크플로 blob과 같은 버전인 최근 아침 발행 작업만 재실행합니다. `auto_release.py`는 새 워크플로 버전마다 초기 실행을 한 번 남깁니다. 과거 다른 코드로 실행한 작업이나 빈 push로 우회하지 않습니다.
5. 발행은 시작 시 최신 안정 `main`을 체크아웃하고 오늘 일일 SHA·전체 CI·허용 파일·동시 변경을 검사합니다. 미확인 초안은 `approve.py --auto`로 공개하며 사람 확인을 기다리지 않습니다.
6. Pages 성공과 공개 색인·호 JSON·홈 내장 데이터·빌드 정보의 날짜·실제 소스 SHA 일치까지 확인합니다. 대기는 한 번에 60초 이하로 나눕니다. 해결되지 않는 자료 누락·검사 실패·충돌만 원인과 실행 기록으로 보고합니다.

코드·기사 임의 수정·검사 생략·강제 push는 하지 않습니다. 기존 네 번의 GitHub 재시도와 평일 14번의 숫자 갱신 배포를 유지합니다. 제공자 예약 지연을 없애거나 정확한 초 단위 발행을 보장하는 구성은 아닙니다.

아침 발행은 일일 소스 SHA의 전체 `verify-ci` 성공을 확인합니다. 이관 전 SHA는 기존 `data`·`browser` 둘 다 요구하며 새 전체 검사 실패를 과거 성공으로 대체하지 않습니다. 안정 코드의 오늘 호가 이미 공개됐으면 중복 발행하지 않으며, 날짜·상태·색인·허용 경로·운영 동시 변경이 어긋나면 중단합니다. 미확인 초안은 검사 후 `approve.py --auto`로 공개하고 `review.auto: true`를 남깁니다. 사람 이름을 만들어 확인자로 적지 않습니다.

`GITHUB_TOKEN` push만으로 후속 워크플로가 실행되지 않으므로 새 운영 자료를 반영한 뒤 배포를 명시적으로 호출합니다. 소스 브랜치에서 바뀐 워크플로나 검사 코드를 아침 발행 코드로 사용하지 않습니다. 배포 작업은 실제 체크아웃한 `deploy` SHA·호 날짜를 공개 빌드 정보에 남깁니다. 호출 응답만으로 공개 완료를 기록하지 않습니다. Pages 실행 환경에서 공개 색인·호 JSON·홈·빌드 SHA와 이번 빌드 시각까지 확인하며 같은 소스가 실패하면 최대 두 번 자동 재시도합니다.

## 이전 구조의 장애 기록

2026.11.03 이전 방식은 `dev` 전체를 `main`·`deploy`로 빨리 감기했습니다. 당시 `main` 병합 커밋이 `dev`에 포함되지 않아 아침 발행이 멈춘 기록과, 2026.10.23의 예약 지연 기록이 인수인계에 남아 있습니다. 이는 **당시 구조의 원인과 복구 사례**이며 현재 일일 브랜치를 `dev`에 합치라는 지시가 아닙니다.

새 구조에서는 일일 자료를 안정 코드에 선별 반영하고, 코드 승격의 조상 관계를 따로 확인합니다. 이전 Claude 예약을 나중에 복구하려면 운영자의 별도 요청에 따라 담당을 하나로 정하고 Codex와 중복 실행되지 않게 합니다. 빠진 날짜는 소급 생성하지 않습니다.
