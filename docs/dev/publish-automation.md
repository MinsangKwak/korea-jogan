# 일일 발행 자동화 구성과 이관 지침

**조간 발행은 저장소 바깥의 예약 작업 2개와 저장소 안의 워크플로 3개가 나눠 맡습니다.** 이 문서는 그 경계와 인수 인계 시 확인할 것을 적습니다. 매일의 조사·작성 절차는 [발행 런북](../planning/runbook.md), 브랜치 규칙은 [브랜치 운영](branches.md)에 있습니다. 시간은 모두 한국 시간입니다.

2026-11-04에 운영자 요청으로 **예약 작업 2개를 모두 껐습니다**. 저장소 워크플로는 그대로 살아 있습니다. 아래 '현재 상태'에서 무엇이 멈췄고 무엇이 도는지 구분합니다.

## 전체 흐름

| 00:00 | 예약 작업 ①(저장소 바깥) | 자료 조사, 호 JSON 작성, 검사, `dev` 커밋 | `data(issue): YYYY-MM-DD호 초안` |

핵심은 **저장소만으로는 조간이 나오지 않는다**는 점입니다. 호 JSON을 만드는 주체가 저장소 밖에 있어서, 그 예약 작업이 멈추면 `publish.yml`은 "오늘 호 없음"으로 조용히 건너뜁니다. 실패 알림이 오지 않으므로 사이트의 호 날짜로 확인해야 합니다.

## 저장소 바깥의 예약 작업

Claude 계정의 예약 작업(routine)으로 돌렸습니다. 저장소 파일이 아니라 계정 설정이므로, 저장소를 넘겨받는 것만으로는 따라오지 않습니다. 이관받는 쪽에서 같은 역할을 새로 만들어야 합니다.

### ① 대한민국 조간 일일 발행

- 주기: 매일 00:00
- 역할: 그날 호 초안 작성
- 지시 내용의 요지
  - `git fetch origin` 후 `dev`를 `origin/dev` 최신으로 맞춥니다.
  - [발행 런북](../planning/runbook.md)을 다시 읽고 그 순서대로 진행합니다.
  - 날짜는 한국 시간 기준이며, 전날 대화 내용이 아니라 그날 새로 수집한 자료만 씁니다.
  - `python3 dev/pipeline/publish/validate.py`를 통과했을 때만 `data(issue): YYYY-MM-DD호 초안`으로 `dev`에 올립니다.
  - `main`·`deploy`에는 직접 올리지 않습니다. 그건 06시 `publish.yml`의 일입니다.
  - 통과하지 못하거나 push가 거부되면 올리지 않고 이유를 보고합니다.
  - 끝나면 `origin/dev`의 색인 `latest`가 그날인지 확인하고, 머리기사·주제 목록·기사 수·대체한 매체를 짧게 보고합니다.

### ② 조간 06:05 아침 발행 보조 실행

- 주기: 매일 06:05
- 역할: `publish.yml`을 손으로 한 번 띄우고 공개를 확인
- 왜 필요했나: GitHub 예약 실행이 정각에 몰려 밀립니다. 2026-10-23에는 06:00 예약이 08:47에 돌았고, 그 뒤로도 3시간 가까이 밀리는 날이 반복됐습니다. `publish.yml`의 예약 시각을 정각에서 비껴 놓고(06:07 등) 재시도를 넷으로 늘렸지만 그래도 밀려서, 06:05에 한 번 직접 띄우는 역할을 따로 뒀습니다.
- 지시 내용의 요지
  - `publish.yml`을 `ref=main`으로 실행합니다. 이미 그날 호가 공개됐으면 워크플로가 알아서 건너뜁니다.
  - 3~5분 기다린 뒤 `https://korea-jogan.com/data/issues/index.json`의 `latest`가 그날인지 15초 간격으로 최대 6분 확인합니다.
  - 공개됐으면 한 줄만 남기고 알림은 보내지 않습니다.
  - 안 됐으면 런북의 실패 순서(초안 존재 → 색인 `latest` → 검사 결과 → 빨리 감기)대로 원인을 확인해 짧게 정리하고 알립니다.
  - **코드나 데이터를 고치거나 강제 push하지 않습니다.**

중복 실행은 안전합니다. `publish.yml`은 `concurrency: publish`로 겹침을 막고, 이미 공개된 호는 빨리 감기 단계에서 건너뜁니다.

## 저장소 안의 워크플로

| 파일 | 실행 조건 | 하는 일 |
| --- | --- | --- |
| [publish.yml](../../.github/workflows/publish.yml) | 06:07·06:37·07:17·08:17 예약, 수동 | 그날 호 상태 확인 → 자동 발행 → 배포 규칙 검사 → `main`·`deploy` 빨리 감기 → 배포 호출 |
| [deploy-pages.yml](../../.github/workflows/deploy-pages.yml) | `deploy` push, 수동, 평일 09:17~22:17 매시 | `deploy` 체크아웃, 검사·파일 생성, Pages 배포 |
| [daily.yml](../../.github/workflows/daily.yml) | 수동만 | RSS·ECOS 원자료 수집. 예약은 주석 처리되어 있음 |

`publish.yml`이 그날 호를 올리는 조건은 둘 다 만족할 때입니다.

1. 색인의 `latest`가 한국 시간 그날 날짜
2. 그날 호의 `status`가 `draft` 또는 `published`

`draft`면 `validate.py` 통과 후 `approve.py --auto`로 바꿔 `review.auto: true`를 남깁니다. 자동 경로에는 사람 이름을 확인자로 쓰지 않습니다.

`GITHUB_TOKEN`으로 올린 push는 다른 워크플로를 띄우지 않으므로, `publish.yml`이 `deploy-pages.yml`을 `gh workflow run`으로 직접 호출합니다. 이 호출을 빼면 브랜치는 올라가지만 사이트가 그대로 남습니다.

## 자주 걸리는 두 가지

### 빨리 감기 실패 — `main`이 `dev`의 조상이 아님

`dev → main` PR을 병합하면 `main`에 병합 커밋이 생기고, 그 커밋은 `dev`에 없습니다. 이 상태로 다음 아침 발행이 돌면 초안 저장·자동 승인·검사까지 모두 통과한 뒤 마지막 단계에서 멈춥니다.

```
##[error]main가 dev의 조상이 아니라 빨리 감기할 수 없습니다. 브랜치를 손으로 맞춘 뒤 다시 실행합니다
```

2026-11-03에 실제로 발생했습니다. 전날 문서 PR을 `main`에 병합하고 `dev`를 맞추지 않은 것이 원인이었습니다.

- **예방**: `dev → main` PR을 병합한 직후, 같은 작업 안에서 `dev`를 그 병합 커밋에 맞춥니다. [브랜치 운영](branches.md)에 적힌 규칙입니다.
- **복구**: `main`을 `dev`에 병합(`git merge origin/main`)해 `dev`가 `main`을 포함하게 만든 뒤 아침 발행을 다시 실행합니다. 파일 내용은 바뀌지 않습니다. 강제 push로 우회하지 않습니다.

### 예약 지연

Actions 예약은 정각에 몰려 밀립니다. 예약 시각은 목표이지 보장이 아닙니다. 그래서 `publish.yml`에 재시도가 넷 있고, 그래도 부족해 06:05 보조 실행을 뒀습니다. 이관 후 보조 실행을 두지 않기로 한다면, 아침에 사이트의 호 날짜를 사람이 확인하는 절차를 대신 넣어야 합니다.

## 현재 상태

| 항목 | 상태 |
| --- | --- |
| 예약 작업 ① 일일 발행(00:00) | 2026-11-04 꺼짐 |
| 예약 작업 ② 보조 실행(06:05) | 2026-11-04 꺼짐 |
| `publish.yml` 예약 | 그대로 실행됨 |
| `deploy-pages.yml` | 그대로 실행됨 |

예약 작업 ①이 꺼져 있으므로 새 호가 만들어지지 않습니다. `publish.yml`은 계속 돌지만 "오늘 호 없음"으로 건너뛰고, 사이트에는 마지막으로 공개된 호가 남습니다. 화면에는 미발행 안내가 나옵니다. 문구만 지우지 않고 실제 발행 상태를 복구합니다.

## 이관 체크리스트

1. **예약 작업 2개를 새로 만듭니다.** 위 ①·② 지시 내용을 그대로 옮기면 됩니다. 저장소 파일이 아니라 계정 설정이라 저장소 권한만으로는 따라오지 않습니다.
2. **00시 작업에 저장소 쓰기 권한을 줍니다.** `dev`에 커밋·push 할 수 있어야 합니다. `main`·`deploy` 권한은 필요 없습니다.
3. **`ECOS_API_KEY`를 확인합니다.** GitHub Secrets에 있습니다. 없으면 최신 숫자 띠만 비고 조간 자체는 나옵니다.
4. **Pages 설정을 확인합니다.** Actions로 배포하며 `github-pages` 환경에서 `deploy` 실행이 허용되어야 합니다.
5. **첫 며칠은 결과를 직접 확인합니다.** 색인 `latest`와 화면의 호 날짜, 그리고 Actions의 아침 발행 로그를 봅니다.
6. **`dev → main` 병합 후 `dev` 맞추기를 인수 인계 내용에 포함합니다.** 위에서 설명한 가장 흔한 실패 원인입니다.

## 다시 켤 때

예약 작업을 지우지 않고 꺼 두었으므로 실행 이력과 지시 내용이 남아 있습니다. 다시 켜면 그다음 00:00부터 같은 방식으로 돕니다. 켜기 전에 확인할 것은 두 가지입니다.

- `origin/dev`·`origin/main`·`origin/deploy`가 갈라져 있지 않은지. 갈라져 있으면 먼저 맞춥니다.
- 꺼져 있던 동안 쌓인 날짜를 소급해 만들지 않습니다. 그날 호부터 다시 시작합니다. 빠진 날은 빠진 대로 둡니다.
