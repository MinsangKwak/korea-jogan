# 커밋 메시지 작성 기준

**제목만 읽어도 변경 내용을 알 수 있게 쓰고, 선택 이유는 본문에 남깁니다.** 채용 담당자와 후속 작업자가 코드의 변화와 판단 과정을 함께 따라갈 수 있는 기록을 목표로 합니다.

## 기본 형식

```text
종류(범위): 변경한 내용

변경이 필요했던 이유와 선택한 방법
```

종류는 소문자, 제목은 한국어로 작성합니다. 검사기는 종류와 범위를 포함한 제목 한 줄 전체를 72자 이내로 제한하며, 제목 끝 마침표를 허용하지 않습니다. 범위와 본문은 필요할 때만 씁니다.

| 범위 | 대상 |
| --- | --- |
| `site` | 화면·탐색·표시 동작 |
| `issue` | 날짜별 호와 정정 데이터 |
| `scripts` | 수집·검사·생성 스크립트 |
| `docs` | README·기획·설계·운영 문서 |
| `infra` | 워크플로·배포·저장소 설정 |

## 종류 선택

| 종류 | 사용 상황 | 예시 |
| --- | --- | --- |
| `feat` | 새 기능 추가 | `feat(site): 홈에서 기준이 다른 숫자 비교 제공` |
| `fix` | 동작·데이터 오류 수정 | `fix(issue): YYYY-MM-DD호 환율 기준일 정정` |
| `style` | 화면 표현·문구 조정 | `style(site): 숫자 카드의 기준일 문구 정리` |
| `refactor` | 동작을 유지한 구조 변경 | `refactor(site): 지역 선택 로직을 컴포넌트로 분리` |
| `docs` | 문서 변경 | `docs(docs): 발행 절차와 실패 대응 기준 정리` |
| `test` | 검사 코드 변경 | `test(scripts): 초안 배포 차단 사례 추가` |
| `data` | 발행 자료 갱신 | `data(issue): YYYY-MM-DD호 초안` |
| `ci` | 자동 검사·배포 설정 | `ci(infra): 배포 전에 토큰 생성 결과 검사` |
| `release` | 여러 변경을 묶은 버전 갱신 | `release: 발행 자동화 개선 반영` |
| `sync` | 브랜치 동기화 | `sync: dev → main` |
| `chore` | 나머지 유지보수 | 구체적인 다른 종류를 먼저 검토 |

한 커밋에는 설명 가능한 주제 하나를 담습니다. 문서별 목적이 다르면 커밋도 나눕니다. PR 제목 역시 같은 형식을 사용합니다.

## 본문에 남길 내용

‘가독성 개선’처럼 의도가 넓다면 무엇을 바꿨는지 구체화합니다. 예를 들어 ‘발행 시각을 06시로 통일하고 사람 확인과 자동 공개를 구분했다’고 쓰면 변경을 다시 읽기 쉽습니다.

성과는 검증 근거가 있을 때만 적습니다. 기능을 추가한 사실을 전환율·검색 순위·정확도 향상으로 바꿔 쓰지 않습니다. 테스트 결과를 적을 때는 실제 실행한 범위를 명시합니다. 공동 작성자 꼬리표는 사실에 맞는 경우 유지합니다.

## 검사 실행

저장소 루트에서 로컬 훅을 설정합니다.

```bash
git config core.hooksPath dev/tools/githooks
```

메시지 파일 하나 또는 커밋 범위를 직접 검사할 수도 있습니다.

```bash
node dev/tools/check_commit_msg.mjs .git/COMMIT_EDITMSG
node dev/tools/check_commit_msg.mjs --range origin/main..HEAD
```

[검사기](../../dev/tools/check_commit_msg.mjs)는 형식·종류·범위·길이·끝 마침표를 검사합니다. 한국어 여부나 본문의 품질까지 판정하지는 않습니다. Git이 생성한 `Merge`·`Revert` 제목은 예외입니다. PR 검사 실패가 병합을 막는지는 저장소 보호 설정에 따릅니다.

이 규칙은 2026-10-19부터 적용한 기록 기준입니다. 과거 이력을 새 규칙에 맞추기 위해 다시 작성하지 않습니다.
