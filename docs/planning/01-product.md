# 서비스 기획과 검증 계획

**대한민국 조간은 독자가 숫자의 출처와 비교 기준을 확인하도록 돕는 서비스입니다.** 뉴스·통계·지역 소식을 한 호에 모으되, 핵심 가치는 기사 수보다 숫자를 다시 확인할 수 있는 흐름에 두었습니다.

## 문제를 어떻게 정의했는가

같은 사건의 수치가 다르다고 해서 어느 한쪽이 반드시 틀린 것은 아닙니다. 비교 시점, 집계 기간, 포함 범위가 다를 수 있습니다. 단순 요약에서는 이 조건이 빠지기 쉬워, 값과 조건을 함께 보여 주는 방식으로 문제를 정의했습니다.

| 관찰한 상황 | 서비스에 반영한 요구사항 |
| --- | --- |
| 같은 지표의 증감률이 기사마다 다름 | 비교 기준과 기간을 나란히 표시 |
| 발표일과 통계 기준일이 다름 | 두 날짜를 별도 필드로 저장 |
| 확정값과 전망값이 함께 인용됨 | 배지·그래프 형태로 상태 구분 |
| 전국 뉴스에서 지역·전통 산업 소식이 묻힘 | 17개 시도와 주력산업을 독립 섹션으로 구성 |
| 매일 많은 기사를 확인해야 함 | 머리기사·핵심 숫자·비교 카드부터 보여 주고 목록은 단계적으로 펼침 |

기존 호에 담긴 비교 사례는 기능을 설명하는 자료입니다. 개별 보도의 오류를 확정하는 근거로 사용하지 않습니다. 원문 확인과 기준 대조가 먼저입니다.

## 먼저 검증할 독자

경제 기사의 숫자를 업무 보고나 개인 판단에 다시 사용하는 30~50대 직장인을 우선 독자 가설로 잡았습니다. 기사마다 다른 수치를 확인하는 일이 실제로 반복되는지, 출처 확인 기능을 사용할지가 검증 대상입니다.

화면은 더 넓은 연령대도 읽을 수 있도록 큰 글자, 짧은 요약, 단순한 이동 구조를 적용했습니다. 이는 사용성을 위한 설계 기준이며, 특정 연령대의 만족도를 검증했다는 뜻은 아닙니다.

| 가설 | 확인할 행동 | 재검토할 신호 |
| --- | --- | --- |
| 독자는 숫자의 차이를 확인하고 싶어 한다 | 홈 비교 카드와 상세 비교 펼치기 | 일반 기사 목록만 사용하고 비교 기능은 거의 열지 않음 |
| 출처를 가까이 두면 확인 행동이 늘어난다 | 출처 펼치기 | 비교는 읽지만 출처를 열지 않음 |
| 주제 탐색이 재사용에 도움이 된다 | 주제 검색과 결과 없음 빈도 | 검색 결과 없음이 반복되거나 특정 주제에만 편중 |

## 정보 구조와 우선순위

홈에서 오늘의 핵심을 보고, 언론 섹션에서 숫자의 차이를 확인한 뒤, 관심 분야로 이동하도록 순서를 정했습니다.

| 순서 | 섹션 | 기획 의도 |
| --- | --- | --- |
| 1 | 홈 | 머리기사·핵심 수치·기준이 다른 숫자로 첫 판단에 필요한 정보 제공 |
| 2 | 언론 | 주제별 요약·수치 비교·기사 링크를 한 흐름으로 연결 |
| 3 | 전국 | 분야별로 하루의 흐름을 확인 |
| 4 | 지역 | 17개 시도를 6개 권역으로 묶어 원하는 지역에 접근 |
| 5 | 정치 | 임기·선거·예산 일정처럼 기준이 명확한 정보 제공 |
| 6 | 경제 | 지수·환율·유가를 출처와 기준일에 연결 |
| 7 | 산업 | 반도체 외 주력산업과 수출입을 상시 제공 |
| 8 | 재정 | 국가채무·월간 재정·국민연금을 장기 추이로 확인 |

모바일에서는 목록을 3건씩 먼저 보여 주고, 하단 탭과 전체 메뉴로 이동 거리를 줄였습니다. 섹션별 분류와 표시 규칙은 [디자인 가이드](../../design/guide.md)에 정리했습니다.

## 범위를 정한 기준

회원·댓글·광고는 초기 범위에서 제외했습니다. 1인 운영에서 계정 관리보다 자료 확인과 발행 안정성에 시간을 쓰기 위한 선택입니다. 정당 공방과 인물 평가는 다루지 않고, 발표·통계·일정을 중심으로 구성합니다.

기사 본문은 저장하지 않습니다. 기사 목록에는 제목과 링크를 두고, 필요한 짧은 요약은 별도로 작성합니다. 수치의 출처를 확인하지 못했다면 추정해서 채우지 않고 누락 또는 미확인 상태를 드러냅니다.

## 신뢰를 화면에 표현하는 방법

| 정보 | 표현 방식 | 목적 |
| --- | --- | --- |
| 출처의 성격 | A 확정 통계·B 잠정 통계·C 정책 발표·D 언론·민간 집계·E 분석·계산 | 자료의 종류를 구분. 등급 자체가 사실성을 보증하지는 않음 |
| 데이터 상태 | 결산·전망 배지와 막대 형태 | 확정값과 미래 추정값 혼동 방지 |
| 확인 여부 | 편집자 확인·자동 발행 표시 | 사람의 원문 대조 여부 공개 |
| 자료의 시점 | 발행일·수집 시각·기준일·발표일 | 오래된 값을 현재 값으로 읽는 문제 완화 |
| 수집 한계 | 본문 열람 여부, 대체 출처, 누락 정보 | 확인 가능한 범위를 독자에게 전달 |
| 오류 수정 | 변경 전후 값과 사유 공개 | 정정 이력 추적 |

## 발행 정책과 운영 책임

00시 예약 작업이 조사·초안 작성·검사를 수행하고 `dev`에 저장합니다. 06시 GitHub Actions는 오늘 호가 있고 검사를 통과했을 때 공개합니다. 사람이 원문과 대조했다면 편집자 확인으로, 확인하지 못했다면 자동 발행으로 표시합니다. 자동 검사는 필수값과 형식·범위 등을 확인하며 내용 검증을 모두 대신하지 않습니다.

자동화 범위와 사람 확인 범위를 나눠 운영 부담을 줄이면서, 독자가 확인 수준을 알 수 있도록 했습니다. 상세 절차는 [발행 런북](runbook.md), 데이터 상태는 [데이터 규격](data-spec.md)에 있습니다.

## 성과를 어떻게 확인할 것인가

현재는 측정 기반을 구현한 단계입니다. GA4 측정 ID는 연결돼 있고 GoatCounter 주소는 비어 있습니다. 실제 수집·집계 결과를 확인하기 전에는 전환율이나 재방문 성과를 제시하지 않습니다.

| 지표 | 계산·확인 방법 | 해석 시 주의점 |
| --- | --- | --- |
| 방문 100회당 확인 행동 수 | `(split-home + split-open + src-open) / 방문 × 100` | 반복 행동을 포함하므로 방문자 비율이 아니며 100을 넘을 수 있음 |
| 출처 확인 횟수 | `src-open`과 출처 기관명 | 펼침 행동이며 외부 원문 방문을 뜻하지 않음 |
| 비교 기능 사용 | `split-home`, `split-open` | 이벤트 합계만으로 사용한 방문 비율을 계산할 수 없음 |
| 검색 수요 | `search`의 주제 이름·결과 없음 | 검색어 원문은 전송하지 않음 |
| 정정 대응 | 오류 신고 이슈와 정정 날짜 | 처리 시간 집계에는 이슈 시각 대조가 필요 |
| 발행 지속성 | 호 목록·워크플로 실행 이력 | 호 존재만으로 정시 배포 성공을 판단하지 않음 |

GA4에서는 이벤트 이름의 하이픈이 밑줄로 바뀝니다. 구현은 [metrics.js](../../dev/web/src/core/metrics.js)를 참조합니다. 측정 ID나 주소를 비우면 해당 도구는 실행하지 않습니다.

## 후속 과제

1. 수집된 행동 데이터를 검토하고 우선 독자 가설을 2주 단위로 확인합니다.
2. 비교 카드와 출처 확인이 적다면 배치·문구·주제 선정부터 조정합니다.
3. KOSIS·관세청·국회 수집을 확장해 수동 조사 범위를 줄입니다.
4. 호가 누적되면 월·연 단위 아카이브를 검토합니다.

기획·화면·발행을 별개 산출물로 끝내지 않고, 사용 행동과 운영 기록으로 다시 판단할 수 있는 구조를 목표로 합니다.
