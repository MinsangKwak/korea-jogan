# 일일 발행과 오류 대응

**00시 Codex가 자료를 조사해 초안을 만들고 문장을 다듬어 저장하며, 06시에는 조건을 충족한 오늘 호를 사람의 검토를 기다리지 않고 공개합니다.** 사람 확인과 자동 발행을 구분해 기록하고, 검사에 실패한 데이터는 공개하지 않습니다. 반복 운영과 장애 복구를 같은 순서로 수행하기 위한 절차이며 시간은 모두 한국 시간입니다.

## 조사 원칙

자료 기준은 전날 23:59까지 발표·보도된 내용이며 시장 숫자는 전 거래일 종가입니다. 발표일·기준일·수집일을 구분합니다. 머리기사는 경제(실적·지표·정책), 안보·외교, 그날 가장 크게 다뤄진 사회 이슈 순으로 고릅니다. 북한 매체 보도·지도자 동선 같은 동향 기사는 전국 뉴스 '안보·외교'에 두되, 우리 쪽 피해·대응·공식 발표가 있으면 머리기사가 될 수 있습니다.

숫자는 공식 발표 또는 그 발표를 인용한 기사에서 확인하고 기억·추측으로 채우지 않습니다. 본문을 읽지 못했다면 `read`·`body_read`를 `false`로 두고 제목·검색 요약만으로 세부를 단정하지 않습니다. 요약은 원문을 복제하지 않고 결론부터 씁니다([편집 기준](editorial.md)). 기사 본문은 저장하지 않으며 정부·정당·인물 평가보다 발표·통계·사실·일정에 집중합니다.

## 1. 작업본 준비

원격을 가져와 안정 `main`의 최신 SHA에서 `daily/YYYY-MM-DD`를 만듭니다. `dev`에서 만들지 않으며 같은 날짜 브랜치가 있으면 상태·SHA를 읽고 덮어쓰지 않습니다. `index.json`이 가리키는 지난 호를 새 호의 틀로 씁니다.

```bash
python3 dev/pipeline/collect/fetch_rss.py --date YYYY-MM-DD
```

결과 `dev/pipeline/collect/raw/rss/YYYY-MM-DD.json`에서 기사 후보와 피드별 성공·실패를 확인합니다. 피드 설정은 [feeds.json](../../dev/pipeline/collect/feeds.json)이며, 피드에 제목이 있다는 사실과 본문 접근 허용은 별개입니다.

## 2. 자료 조사

| 영역 | 수집 범위·작성 기준 |
| --- | --- |
| `nums` | 전 거래일 지수·환율, 두바이유·휘발유 평균가. 기관과 원문 링크 필수 |
| `national` | 8개 분야에서 2~4건씩 총 18~24건 목표와 흐름 3줄 |
| `regions` | 17개 시도별 2~3건 목표(수도권·강원·충청 / 영호남·제주로 나눠 조사), 지역 매체 우선, 시도별 한 줄 요약 |
| `themes` | 주요 주제 2~3개, 국내 매체 8곳 이상 목표, 관련 해외 기사, 요약·수치 비교·키워드 |
| 상설 지표 | 재정·국가채무·국민연금·수출입·산업. 새 공식 발표가 있을 때만 갱신, 기존 기준일 유지 |
| `trackers.json` | 새 단계·기사가 나온 날만 `updated`와 함께 갱신 |

기사 수는 편집 목표이며 검사가 보장하지 않습니다. 부족하면 날짜 범위와 누락을 `limits`에 공개하고 기사를 만들지 않습니다. `ECOS_API_KEY`가 있으면 공식 숫자를 먼저 수집합니다.

```bash
python3 dev/pipeline/collect/fetch_ecos.py --date YYYY-MM-DD
python3 dev/pipeline/collect/ecos_nums.py YYYY-MM-DD
```

## 3. 초안 작성과 저장

`status: draft`로 호 파일을 쓰고 색인의 `latest`·`issues`에 오늘을 넣습니다. 발행일·수집 시각·머리기사·핵심 수치 3개·꼭 볼 숫자 4~6개·일정·당일 뉴스는 새로 정리하고 이월 지표는 기준일·출처를 유지합니다.

```bash
python3 dev/pipeline/publish/validate.py
```

실패 메시지는 `파일: 필드` 형태로 고칠 곳을 지목하므로 그 항목부터 수정합니다. 지난 자료를 유지하면 `limits`에 이유를 적고 오래된 값을 오늘 확인한 값처럼 바꾸지 않습니다. 해결하지 못하면 발행을 중단하고 보고합니다. 커밋은 `data(issue): YYYY-MM-DD호 초안`(편집까지 마쳤으면 그 역할을 드러내는 제목), 추적 갱신은 별도 커밋. 예상 SHA로 오늘 `daily`에 반영하고 그 SHA의 CI를 확인합니다.

### 3.5 저장 전 문장 편집

사실 초안을 임시 파일로 보존하고 `validate.py`를 먼저 실행한 뒤, [편집 기준](editorial.md)의 허용 문자열만 수정합니다. 편집 후 `check_editorial.py --baseline-file <사실 초안> --date YYYY-MM-DD` → `validate.py` 순서로 검사합니다(이미 원격에 있는 초안은 `--base-ref <SHA>`). 대상 `daily`의 시작 SHA가 그대로일 때만 반영하고 동시 변경은 덮어쓰지 않고 보고합니다. 승인·공개는 이 단계에서 하지 않습니다.

## 4. 사람 확인 또는 자동 공개

사람이 확인할 때는 `python3 -m http.server -d dev/web 8000`으로 로컬 화면을 열어 `lead`·`nums`·`themes[].diffs`를 원문과 대조한 뒤에만 실행합니다.

```bash
python3 dev/pipeline/publish/approve.py YYYY-MM-DD --by 이름
python3 dev/pipeline/publish/validate.py --deploy
```

확인한 호는 `data(issue): YYYY-MM-DD호 승인`으로 오늘 `daily`에 저장합니다. 06시까지 확인이 없으면 워크플로가 `approve.py --auto`로 전환해 `data(issue): YYYY-MM-DD호 자동 발행` 커밋을 남깁니다. 자동 경로에는 사람 이름을 쓰지 않으며, `published`는 공개 상태일 뿐 `review.auto`가 확인 여부를 구분합니다. 이미 공개된 호에 승인 명령을 반복하지 않습니다.

## 5. 반영과 배포 확인

`publish.yml`은 안정 `main` 코드로 오늘 `daily`의 정확한 SHA와 `verify-ci` 성공을 확인하고 [prepare_daily.py](../../dev/pipeline/publish/prepare_daily.py)로 오늘 JSON·색인·실제 추적 변경만 가져옵니다(허용 경로·색인 보존·동시 변경 검사는 [보호 조건](../dev/branches.md#일일-발행-경로의-보호-조건)). 미확인 초안을 자동 공개하고 `main`·`deploy`에 원자적으로 push한 뒤 Pages를 명시적으로 호출합니다. 일일 브랜치 전체나 `dev` 코드는 병합·실행하지 않습니다.

`deploy-pages.yml`은 `validate --deploy` → `build_feed.py` → `build_pages.py`(호별 HTML·CSP 해시) → `build_live.py`(실패해도 계속) → `build_info.py` → Pages 순서로 진행하고 공개 색인·호 JSON·홈·`build-info.json`의 날짜·SHA를 대조합니다. 06시를 넘겨 수집했다면 자료 기준은 전날 23:59로 두고 `late.reason`·`late.cutoff`를 남기며 수집 시각을 앞당겨 적지 않습니다.

06:05 Codex 감독은 다음 순서로 수행합니다.

1. 현재 `main`의 지침·워크플로, 오늘 날짜, 공개 색인·호 JSON·홈·빌드 SHA를 확인합니다. 공개됐으면 한 줄 결과만 남깁니다.
2. 미공개면 진행 중인 아침 발행·같은 소스의 Pages를 확인하고, 진행 중이면 중복 시작하지 않습니다.
3. 실행이 없거나 실패했다면 `publish.yml`을 `ref=main`으로 실행합니다. 직접 실행 도구가 없으면 현재 `main`의 워크플로 blob과 같은 버전의 최근 아침 발행 작업만 재실행합니다. 과거 다른 코드의 작업이나 빈 push로 우회하지 않습니다.
4. Pages 성공과 공개 색인·호 JSON·홈 내장 데이터·빌드 정보의 날짜·소스 SHA 일치까지 확인합니다. 대기는 한 번에 60초 이하로 나누고, 해결되지 않는 누락·검사 실패·충돌만 원인과 실행 기록으로 보고합니다.

코드·기사 임의 수정·검사 우회·강제 push는 하지 않습니다. 배포 호출 응답만으로 완료 처리하지 않고 아래 주소를 대조합니다.

- [공개 색인](https://korea-jogan.com/data/issues/index.json) · [배포 정보](https://korea-jogan.com/build-info.json) · [서비스](https://korea-jogan.com/)

UI를 바꾼 경우 배포 뒤 [디자인 가이드](../../design/guide.md)의 배치·펼침·순환·테마 기준대로 PC·모바일을 확인하고, 호별 HTML·관리자의 CSP 해시는 `build_pages.py`가 갱신하므로 오래된 해시를 수동으로 유지하지 않습니다.

## 장애 추적 순서

발행이 안 됐을 때 **코드 실패·데이터 실패·예약 지연·배포 실패**를 먼저 구분합니다. 순서대로 보면 보통 한 곳에서 멈춥니다.

| 순서 | 볼 곳 | 여기서 갈리는 것 |
| --- | --- | --- |
| 1 | Actions `아침 발행` 실행 목록의 실제 시작 시각 | 실행 자체가 없으면 **예약 지연**. 실패가 있으면 2번으로 |
| 2 | `publish.yml` `source` 단계: `run`/`existing`/`source_sha` | "06시 전", "오늘 호 이미 공개", "`daily` 없음" 중 어느 분기로 끝났는지 |
| 3 | `선택한 일일 커밋의 CI 확인` → 그 SHA의 `verify-ci` | 일일 후보의 데이터·토큰·Python·브라우저 6개 파일 중 어느 단계가 실패했는지 |
| 4 | `prepare_daily.py` 메시지 | 허용 경로 밖 변경, 색인 보존 실패, `main` 동시 변경, 추적 `updated` 불일치 |
| 5 | `validate.py` 로그의 `파일: 필드` | 데이터 자체 오류. 메시지가 가리키는 필드만 고친다 |
| 6 | `push` 단계 | 확인 중 `main`/`daily`가 바뀜, 조상 관계 아님 → 재실행. 강제 push 금지 |
| 7 | `사이트 배포` 실행 | `validate --deploy`·`build_*`·Pages 중 어디서 멈췄나. `build_live` 실패는 배포를 막지 않음 |
| 8 | 공개 색인·`build-info.json`·`/YYYY-MM-DD` | `latest`·`sourceSha`·`issueDate`가 같은 날짜·SHA인가. 다르면 배포는 됐지만 다른 소스 |

| 증상 | 먼저 확인 | 대응 |
| --- | --- | --- |
| 오늘 호가 없음 | Codex 실행·오늘 `daily`·JSON | `main`에서 초안 준비·검사해 `daily` 저장·CI 확인 후 재실행 |
| 보안 검사에서 관리자 공개 호 대기 실패 | 임시 공개 HTML의 호 목록과 관리자 JSON 색인 일치 | `published_index()`로 색인을 맞춘 뒤 후보 SHA의 전체 `verify-ci` 재확인. 초안 차단은 해제하지 않음 |
| 반영 충돌 | 일일 시작 기준·현재 안정본·오늘 호·추적 변경 | 필요한 변경을 보존해 다시 조사·검증. `dev` 전체 병합·강제 push로 우회하지 않음 |
| 최신 숫자 띠만 없음 | ECOS 키·수집 로그·`live.json` | 조간과 분리해 조사. 호 JSON은 바꾸지 않음 |

지난 호가 표시될 때 화면의 미발행 안내 문구만 지우지 않고 실제 발행 상태를 복구합니다.

### 11/05 복구를 예로 든 추적

2026.11.05에는 위 3번에서 관리자 공개 호 표시 대기가 실패했습니다. 임시 HTML은 공개 호만 담았지만 JSON 색인에는 초안이 남아 있어, `published_index()`로 같은 공개 목록을 사용하도록 고쳤습니다. 검사 조건을 유지한 채 후보 CI부터 공개 데이터 대조까지 확인했습니다.

예약이 늦게 시작한 현상은 별도로 조사했으며 검사 실패와 같은 원인으로 묶지 않았습니다. 당시 SHA·검사·복구 시각과 CSP 대기 오류의 전체 이력은 [변경 기록](../dev/changelog.md#20261105-발행-복구와-운영-확인)에 모았습니다. 이 사례는 감독 예약의 상시 수정 권한을 뜻하지 않습니다.

## 정정

오류 신고를 받으면 원문과 기준부터 대조합니다. 확인되면 해당 호 JSON과 `corrections.json`을 같은 커밋에서 수정하고 변경 전후 값·이유·정정일을 기록해 `fix(issue): YYYY-MM-DD호 항목 정정`으로 커밋합니다. 과거 호 정정은 오늘 호만 다루는 아침 발행 조건과 다르므로 일반 브랜치·배포 절차로 반영하고 신고 이슈에 커밋을 연결합니다. 형식은 [정정 데이터](data-spec.md#correctionsjson)입니다.

## 접속이 막힌 매체

본문 접근이 막히면 우회하지 않고 허용된 다른 출처로 대체합니다. 읽지 못한 기사는 열람 표시를 `false`로 남기고 대체·누락은 `limits`에 적습니다. RSS 수집기는 공개 피드의 제목·링크·날짜만 쓰며 피드가 있어도 본문은 차단될 수 있으므로 특정 매체의 성공 여부를 고정 사실로 적지 않고 실행 결과의 `feeds`를 확인합니다.

## 장기 이슈 갱신

`trackers.json`은 새 기사나 확인된 단계가 생겼을 때만 갱신하며 `updated`는 자료 대조일입니다.

1. 기사 보도일·매체·원문 주소와 실제 확인 범위를 남깁니다.
2. 발생한 일은 `steps`, 편집상 현재 단계는 `phases`·`phaseIndex`, 남은 확인은 `next`로 분리합니다.
3. 확정 기한이 없으면 `periodUnknown: true`로 두고 `start`·`end`·기간 완료율을 넣지 않습니다.
4. 예정일이 지났다는 이유로 완료 처리하지 않고 송치·기소·유죄 확정을 구분합니다.
5. 검사 후 최신 호의 2면·추적 패널을 확인하고 지난 호에는 현재 기록이 숨겨지는지 확인합니다.
