## 조사 원칙

자료의 기준은 전날 23:59까지 발표·보도된 내용입니다. 시장 숫자는 전 거래일 종가를 사용하며, 당일 장중 자료를 섞지 않습니다. 발표일·기준일·수집일은 구분합니다.

머리기사는 한국 독자의 판단에 바로 쓰이는 발표·사건에서 고릅니다. 경제(실적·지표·정책), 안보·외교, 그날 가장 크게 다뤄진 사회 이슈 순으로 봅니다. 북한 매체 보도나 지도자 동선 같은 동향 기사는 머리기사로 쓰지 않고 전국 뉴스의 '안보·외교'에 둡니다. 북한이 얽힌 사안이라도 우리 쪽 피해·대응·공식 발표가 있으면 안보 사안으로 보고 머리기사가 될 수 있습니다.

숫자는 공식 발표 또는 그 발표를 인용한 기사에서 확인합니다. 기억과 추측으로 채우지 않습니다. 본문을 읽지 못했다면 `read`·`body_read`를 `false`로 두고, 제목·검색 요약만으로 세부 수치나 맥락을 단정하지 않습니다.

요약은 원문을 복제하지 않고 확인한 범위에서 결론부터 읽기 쉽게 작성합니다. 문장 수를 고정하지 않으며 대상·조건·배경·남은 확인을 필요한 만큼 연결합니다. [초안 편집 기준](editorial.md)을 따릅니다. 언론 주제 기사 목록에는 제목·매체·날짜·열람 여부와 링크를 저장하며 기사 본문은 저장하지 않습니다. 정부·정당·인물에 대한 평가보다 발표·통계·사실·일정에 집중합니다.

## 1. 작업본 준비

원격을 가져와 안정 `main`의 최신 SHA를 확인하고 그 기준에서 `daily/YYYY-MM-DD`를 만듭니다. 개발 `dev`에서 만들지 않습니다. 같은 날짜 브랜치가 있으면 상태·SHA를 읽고 덮어쓰지 않습니다. 로컬 작업을 보존하며 한국 시간 오늘 날짜를 정합니다. `dev/web/data/issues/index.json`이 가리키는 지난 호를 새 호의 틀로 사용합니다.

RSS 목록을 먼저 수집합니다.

```bash
python3 dev/pipeline/collect/fetch_rss.py --date YYYY-MM-DD
```

결과는 `dev/pipeline/collect/raw/rss/YYYY-MM-DD.json`입니다. 기사 후보와 피드별 성공·실패를 확인합니다. RSS에 제목이 있다는 사실과 본문 접근 허용 여부는 별개입니다.

## 2. 자료 조사

조사 자동화는 아래 역할로 나눠 병렬 수행합니다. 각 조사 작업에 원칙과 지난 호의 동일 항목 구조를 전달합니다. 이 역할 분담은 일일 조사에 적용하며 다른 개발 작업에 일괄 적용하지 않습니다.

| 조사 영역 | 수집 범위·작성 기준 |
| --- | --- |
| 핵심 숫자 `nums` | 전 거래일 지수·환율, 두바이유·휘발유 평균가. 기관과 원문 링크 필수 |
| 전국 `national` | 8개 분야에서 2~4건씩, 총 18~24건 목표와 흐름 3줄 |
| 지역 `regions` | 17개 시도별 2~3건 목표, 지역 매체 우선, 시도별 한 줄 요약 |
| 언론 `themes` | 주요 주제 2~3개, 국내 매체 8곳 이상 목표, 관련 해외 기사, 흐름 있는 요약·수치 비교·키워드 |
| 상설 지표 | 재정·국가채무·국민연금·수출입·산업. 새 공식 발표가 있을 때 갱신 |
| 추적 `trackers.json` | 결론이 날 때까지 보는 사안. 새 단계·기사가 나온 날만 `updated`와 함께 갱신 |

지역 조사는 수도권·강원·충청과 영호남·제주로 나눕니다. 기사 수는 편집 목표이며 검사 스크립트가 충족 여부를 보장하지 않습니다. 자료가 부족하면 날짜 범위와 누락 사실을 공개하고 숫자를 맞추기 위해 기사를 만들지 않습니다.

`ECOS_API_KEY`가 있으면 공식 숫자를 먼저 수집·변환합니다.

```bash
python3 dev/pipeline/collect/fetch_ecos.py --date YYYY-MM-DD
python3 dev/pipeline/collect/ecos_nums.py YYYY-MM-DD
```

`dev/pipeline/collect/raw/ecos/YYYY-MM-DD.nums.json`의 코스피·코스닥·환율·기준금리를 우선 확인합니다. 조간에 사용할 기준일과 맞는지도 대조합니다. API 키는 GitHub Secrets로 관리합니다.

## 3. 초안 작성과 저장

날짜별 호 파일을 작성하고 `status`는 `draft`로 둡니다. 발행일·수집 시각·머리기사·핵심 수치 3개·오늘 꼭 볼 숫자 4~6개·일정·당일 뉴스는 새로 정리합니다. 이월한 상설 지표는 기존 기준일과 출처를 유지합니다.

색인의 `latest`를 오늘로 바꾸고 `issues` 앞에 오늘 날짜를 넣습니다. 검사 후 통과한 초안만 오늘 `daily`에 저장합니다. 허용 변경은 오늘 JSON·색인·실제 새 추적 근거이며 코드·문서·과거 호를 함께 올리지 않습니다.

```bash
python3 dev/pipeline/publish/validate.py
```

검사 실패는 해당 항목부터 수정합니다. 부득이하게 지난 호 자료를 유지하면 이전 기준일을 보존하고 `limits`에 이유를 적습니다. 오래된 값을 오늘 확인한 값처럼 바꾸지 않습니다. 해결하지 못하면 발행을 중단하고 실패 이유를 보고합니다.

커밋 제목은 `data(issue): YYYY-MM-DD호 초안`입니다. 문장 편집을 함께 마쳤다면 역할을 드러내는 제목으로 남깁니다. 추적 갱신은 별도 커밋으로 나누며 예상 SHA로 오늘 `daily`에 반영하고 그 SHA의 CI를 확인합니다. 저장 후 머리기사·핵심 숫자·기준이 다른 숫자와 원문 링크를 확인 대상으로 정리합니다.

## 3.5. 저장 전 초안의 문장 흐름 편집

00시 Codex 조사 작업 안에서 사실 초안 작성 뒤 편집합니다. 기존 Claude 조사·보조 예약은 꺼진 상태로 이관하며, 별도 01시 작업은 두지 않습니다. 이미 공개된 호를 자동 재작성하지 않습니다.

[초안 편집 기준](editorial.md)의 허용 문자열만 수정합니다. 조사 직후 사실 초안을 임시 파일로 보존하고 먼저 `validate.py`를 실행합니다. 원문과 대조하며 결과·근거·독자에게 필요한 조건을 짧은 문단으로 연결하고 수치·단위·날짜·인용 주체·추정·예정·미열람 표시는 유지합니다.

편집 후 `check_editorial.py --baseline-file <사실 초안 파일> --date YYYY-MM-DD`, `validate.py` 순서로 검사합니다. 이미 있는 오늘 초안은 `--base-ref <기준 40자리 SHA>`로도 대조할 수 있습니다. [명령과 검사 한계](editorial.md#00시-한-번의-실행-순서)를 확인합니다. 오늘 초안+색인과 실제 근거가 바뀐 추적 자료는 역할별 커밋을 나누며, 대상 `daily`의 시작 SHA가 그대로일 때만 예상 SHA로 직접 반영합니다. 동시 변경이 있으면 덮어쓰지 않고 보고합니다. 승인·공개는 이 단계에서 하지 않습니다.

## 4. 사람 확인 또는 자동 공개

사람이 확인할 때는 로컬 화면을 열어 `lead`, `nums`, `themes[].diffs`를 원문과 대조합니다. 실제 확인 이후에만 아래 명령을 실행합니다.

```bash
python3 -m http.server -d dev/web 8000
```

대조를 마친 뒤 별도 터미널에서 실행합니다.

```bash
python3 dev/pipeline/publish/approve.py YYYY-MM-DD --by 이름
python3 dev/pipeline/publish/validate.py --deploy
```

확인한 호는 `data(issue): YYYY-MM-DD호 승인`으로 오늘 `daily`에 저장하고 새 SHA의 CI를 확인합니다. 06시까지 사람이 확인하지 못한 초안은 워크플로가 검사 후 `approve.py --auto`로 전환하고 `data(issue): YYYY-MM-DD호 자동 발행` 커밋을 남깁니다. 자동 경로에는 사람 이름을 확인자로 쓰지 않습니다.

`published`는 공개 상태를 뜻합니다. 사람 확인 여부는 `review.auto`로 구분하며, 자동 검사가 원문의 정확성까지 보증하지는 않습니다.

## 5. 브랜치 반영과 배포 확인

06:05 Codex 예약은 현재 공개 날짜·워크플로 기록을 읽기 전용으로 확인합니다. 연결 도구에 수동 실행 기능이 없고 대체 재실행의 자동 승인 검토가 거절돼, 원래 요청한 `publish.yml` 직접 실행은 별도 승인·실행 경로 확인 대기입니다. 기존 GitHub 예약이 실제 발행을 맡습니다. 3~5분 뒤 공개 색인의 오늘 날짜를 15초 간격으로 최대 6분 확인하며 대기는 한 번에 60초 이하로 나눕니다. 성공하면 한 줄 결과만 남기고 별도 알림은 보내지 않습니다. 실패하면 오늘 일일 브랜치·색인·고정 SHA의 CI·선별 검사·Pages를 읽기 전용으로 진단해 알립니다. 코드·데이터 수정, 빈 push 우회, 강제 push는 하지 않습니다. [현재 실행 범위](editorial.md#0605-공개-확인의-현재-실행-범위)를 확인합니다.

06시 워크플로는 안정 `main` 코드로 오늘 `daily`의 정확한 SHA와 CI 성공을 확인합니다. 오늘 JSON·색인·실제 추적 변경만 선별해 가져오고 허용 경로·날짜·운영 동시 변경을 검사합니다. 미확인 초안은 자동 공개하고 안정 코드에 데이터 커밋을 만든 뒤 `main`·`deploy`에 반영해 Pages를 호출합니다. 일일 브랜치 전체나 `dev` 코드는 병합·실행하지 않습니다. [브랜치별 반영 기준](../dev/branches.md#일일-발행)을 따릅니다.

배포 워크플로는 초안 차단을 다시 확인하고 RSS·사이트맵·호별 HTML·최신 숫자를 생성합니다. 06시 이후 초안을 준비하거나 확인했다면 Actions의 아침 발행을 수동 실행합니다. 06시를 넘겨 수집했다면 자료 기준은 그대로 전날 23:59로 두고, 호에 `late`(늦은 이유와 `cutoff`)를 남깁니다. 화면은 늦게 수집한 호라고 알립니다. 수집 시각을 앞당겨 적지 않습니다. 이미 공개 상태인 호에 승인 명령을 반복 실행하지 않습니다.

배포 호출 응답만으로 완료 처리하지 않습니다. 해당 SHA의 Pages 성공 뒤 아래 주소의 날짜·실제 배포 소스 SHA를 대조하고 화면의 호 날짜·확인 상태·주요 섹션을 확인합니다.

- [최신 호 색인](https://korea-jogan.com/data/issues/index.json)
- [실제 배포 정보](https://korea-jogan.com/build-info.json): 소스 SHA·호 날짜
- [서비스 화면](https://korea-jogan.com/)

최신 숫자 띠는 조간과 별개입니다. 평일 매시 배포 시 ECOS에서 갱신하며 장중 시세를 제공하지 않습니다. 띠 수집에 실패해도 조간 자체는 배포할 수 있습니다.

### 화면과 발행을 함께 확인하기

배포 완료 뒤 최신 호·지난 호의 날짜와 표시 상태를 먼저 확인합니다. UI를 바꾼 경우에는 아래 동작도 확인합니다.

- PC: 이슈 카드 두 열, 머리기사 옆 목록의 높이·스크롤, 제목 옆 검색과 산업 그래프 배치.
- 모바일: 요약·단계·대표 숫자·기준일·검색 상시 표시, 보조 영역 기본 접기와 펼침 동작.
- 경제: 실제 순환 이동·이전/다음·재생 제어, 출처를 읽을 때 자동 넘김 중지, 원문 기준일 보존.
- 지난 호: 해당 호 데이터 유지, 현재 추적과 자동 갱신 숫자 숨김, 이전 주소의 날짜 이동.
- 실패 화면: 로딩 종료·대체 요약·다시 불러오기. 검사 통과와 원문 사실 확인은 구분.

브라우저 회귀 검사는 저장소 루트에서 아래 폴더로 이동한 뒤 실행합니다.

```bash
cd dev/tests/browser
npm ci
npx playwright install chromium
npm test
```

호별 HTML과 관리자 페이지의 CSP 해시는 배포 시 [build_pages.py](../../dev/pipeline/build/build_pages.py)가 최종 내용에 맞춰 갱신합니다. 인라인 코드를 바꾼 뒤 오래된 해시를 수동으로 유지하지 않습니다.

## 발행 실패 대응

| 증상 | 먼저 확인할 것 | 대응 |
| --- | --- | --- |
| 오늘 호가 없음 | Codex 실행·오늘 `daily`·날짜별 JSON | 안정 `main`에서 초안을 준비·검사해 오늘 `daily` 저장·CI 확인 후 운영자가 재실행 |
| 파일은 있으나 공개되지 않음 | 오늘 `daily`의 고정 SHA·CI·색인·허용 경로 | 실패 항목·운영 동시 변경을 확인한 뒤 검증·재실행 |
| 검사 실패 | 로그의 파일·필드 | 값을 수정하거나 누락·이전 기준을 명시하고 재검사 |
| 반영 충돌 | 일일 시작 기준·현재 안정본·오늘 호와 추적 변경 | 필요한 변경을 보존해 다시 조사·검증. 전체 `dev` 병합·강제 push로 우회하지 않음 |
| Pages 배포 실패 | 배포 작업 로그와 환경 허용 브랜치 | 실패 단계·환경 설정을 확인하고 재실행 |
| 최신 숫자 띠만 없음 | ECOS 키·수집 로그·`live.json` 생성 | 조간과 분리해 조사. 호 JSON을 임의 변경하지 않음 |

지난 호가 표시될 때는 화면에 미발행 안내가 나옵니다. 문구만 지우지 않고 실제 발행 상태를 복구합니다.

## 정정

오류 신고를 받으면 원문과 기준부터 대조합니다. 오류가 확인되면 해당 호 JSON과 `corrections.json`을 함께 수정합니다. 변경 전 값·변경 후 값·이유·정정일을 기록하고 `fix(issue): YYYY-MM-DD호 항목 정정`으로 커밋합니다.

재검사 후 일반 브랜치·배포 절차로 반영합니다. 과거 호 정정은 오늘 호만 처리하는 아침 발행의 조건과 다를 수 있으므로 [브랜치 절차](../dev/branches.md)를 따릅니다. 신고 이슈에는 반영 커밋을 연결해 처리 결과를 남깁니다. 형식은 [정정 데이터](data-spec.md#correctionsjson)를 참조합니다.

## 접속이 막힌 매체

본문 접근이 막히면 우회하지 않고 허용된 다른 출처로 대체합니다. 읽지 못한 기사의 열람 표시는 `false`로 남기고, 대체나 누락은 `limits`에 적습니다.

RSS 수집기는 공개 피드에서 제목·링크·날짜를 사용하며 본문을 저장하지 않습니다. 피드가 있어도 본문은 차단될 수 있고, 피드 자체가 실패하거나 날짜가 없어 전날 목록에서 빠질 수도 있습니다. 특정 매체의 성공 여부를 고정 사실로 적기보다 실행 결과의 `feeds`를 확인합니다. 피드 설정은 [feeds.json](../../dev/pipeline/collect/feeds.json)에서 관리합니다.

## 장기 이슈 갱신

`trackers.json`은 새 기사나 확인된 단계가 생겼을 때 갱신합니다. `updated`는 자료 대조일이며, 과거 기사를 오늘의 공식 발표로 읽히게 만들지 않습니다.

1. 기사 보도일·매체·원문 주소와 실제 확인 범위를 남깁니다.
2. 발생한 일은 `steps`, 편집상 현재 단계는 `phases`·`phaseIndex`, 남은 확인은 `next`로 분리합니다.
3. 확정 기한이 없으면 `periodUnknown: true`로 두고 `start`·`end`와 기간 완료율을 넣지 않습니다.
4. 예정일이 지났다는 이유로 완료 처리하지 않고, 송치·기소·유죄 확정도 구분합니다.
5. 검사 후 최신 호의 2면·추적 패널을 확인하고, 지난 호에는 현재 기록이 숨겨지는지 확인합니다.

현재 추적 목록은 [trackers.json](../../dev/web/data/trackers.json)을 기준으로 봅니다. 2026.10.30 무안공항 자료의 확인 범위는 [당시 근거 기록](../research/muan-airport-20261030.md), 최신 배치와 검사 범위는 [현재 변경 기록](../dev/changes-2026-11-03-sections.md)에 있습니다.

검색 노출을 늘리기 위한 외부 링크 작업은 [외부 링크 늘리기](backlinks.md)에 분리했습니다.

## 요약을 읽기 쉽게 쓰는 기준

첫 문장에 독자가 알아야 할 결과·변화·현재 상태를 씁니다. 다음 문장에 수치·기준일·발표 주체를 연결하고, 배경과 남은 확인 사항은 마지막에 둡니다. 서로 다른 사건은 긴 연결 문장으로 묶지 않고 각각 나눕니다.

- 기사 제목·숫자·단위·출처·날짜·확인 기록은 문체 수정으로 바꾸지 않습니다.
- 혐의·추정·예정·전망·미확정 등 근거의 한계를 그대로 남깁니다. 계획을 완료로 바꾸지 않습니다.
- 최신호의 문구를 고칠 때 과거 호를 일괄 변경하지 않습니다. 의미·사실을 수정했다면 기존 정정 절차를 따릅니다.
- 형식 검사 외에 수정 전후 숫자·링크·날짜·review·단계 상태를 대조합니다. 읽기 개선이 사실 확인을 대신하지 않습니다.

화면은 긴 요약의 첫 문장을 강조해 나누지만 내용을 생략하거나 새 사실을 생성하지 않습니다. 반복 편집의 허용 필드·원문 재확인·사실 보존·동시 변경 처리는 [초안 편집 운영](editorial.md)에 따릅니다.
